# Contributing

## What you need

A CUDA capable GPU is required to run the execution tests, the benchmarks and
the profiler. It is **not** required to build the project or to run the host
tests, which cover configuration parsing, the snapshot format, the smoothing
kernels, the spatial hash and the initial condition generators. Device entries
on a machine without a GPU show as Skipped rather than passed, with the reason
stated, so a run there is honest rather than merely green.

Toolchain floors, all verified on the reference machine:

- CUDA Toolkit 13.3 or newer
- GCC 15 (nvcc 13.3 refuses anything newer)
- CMake 3.28 or newer
- Python 3 with the packages in `requirements.txt` for the figures
- TeX Live with latexmk, and poppler for `pdftotext`, for the reports

## Building

```bash
cmake --preset dev
cmake --build --preset dev
ctest --preset dev
```

`make setup` and `make build` do the same first two steps. The options live in
`CMakePresets.json`, and `CMakeUserPresets.json` is ignored for your own.

The `dev` preset configures with fast math on. That switch reaches only the
benchmark library. The validation library is compiled from identical sources
with fast math forced off, so a physics gate can never be relaxed by a compiler
flag.

The default build targets `sm_120`. The `release-fat` and `ci` presets build
`physics_core` for `75;80;86;89;90;120`, which continuous integration and
releases use. The `host-only` preset needs no CUDA toolkit.

The binaries land in `build/bin`: `cuda_physics_sim`, `gpu_probe`, `bench_all`,
`unit_tests_host`, `validation_tests_host`, `unit_tests_gpu`, `integration_tests`
and `validation_tests`.

## Test levels

There are six ctest entries. Test counts are from `--gtest_list_tests` on this tree.

| ctest entry | run with | needs a GPU | tests | what it covers |
|---|---|---|---:|---|
| `unit_host` | `make test-host` | no | 297 | formulas, parsing, snapshot format, initial conditions, CLI, benchmark rows |
| `validation_host` | `make test-host` | no | 14 | the gates that need no device, such as kernel normalisation and Plummer density |
| `doc_numbers_tool` | `make test-host` | no | | the number checker itself |
| `unit_gpu` | `make test-gpu` | yes | 17 | reductions, kernel parity across all variants |
| `integration` | `make test-gpu` | yes | 62 | 100 step smoke per solver, snapshot and resume bit identity, diagnostics, input safety |
| `validation` | `make validate` | yes | 14 | the device physics gates |

Run everything with `make test`. `make validate` runs both validation entries.

## Before opening a pull request

```bash
make check-style   # the dash gate, must be silent
make build         # warnings are errors, so a clean build is the gate
make test
```

## House rules

**No en dashes or em dashes anywhere.** Not in source, not in documentation, not
in the compiled PDFs. `scripts/check_no_dashes.py` enforces it and runs as part
of the report build. In LaTeX prose never type two hyphens: TeX turns them into
an en dash silently, and `\texttt` does not suppress it, only a verbatim region
does. Write ranges as "10 to 20".

**No number without a run.** Any performance figure in the documentation or the
reports must come from a file written by a program in this repository. The
figures and tables are generated by `scripts/plot_results.py` and
`scripts/gen_report_assets.py` from the recorded CSVs. LaTeX quotes measured values
through the macros in `report/numbers.tex`. Markdown marks them as
`<!-- num:RepeatabilitySpread -->1.2<!-- /num -->`, and
`scripts/check_doc_numbers.py` fails on a mark that disagrees with
`docs/generated_numbers.md`. If you need a metric that does not exist, add it to
`scripts/gen_report_assets.py`. A value that describes `v1.0.0` in a correction
record is the one exception, and must be labelled as such.

**Recording is deliberate.** An ordinary test run writes to the build tree and
leaves `experiments/results` alone. `make record-results` is the only target that
updates the committed gate values, and `make bench` replaces benchmark rows. Commit
first: `bench_all` refuses a dirty tree, and `scripts/check_provenance.py` fails on any
row whose commit does not resolve or was measured under another protocol. If you change
a kernel, rerun `make bench` and regenerate.

**A claim must clear the drift.** A performance difference is quoted only if it
exceeds the session drift, the `RepeatabilitySpread` metric, or it is worded as not
resolved. Compare variants with the paired ratios from the raw trials, with their IQR.

**Physics gates are hard gates.** A failing conservation test is a stop the line
defect. Do not loosen a tolerance without a written justification in
`docs/ENGINEERING_LOG.md` explaining why the new value is the physically correct
bound.

**Express tolerances relative to a scale.** Never an absolute tolerance against
a quantity whose magnitude you have not stated. Use the magnitude of the value,
the machine epsilon, or a bound derived from the arithmetic.

**Zero warnings.** The build runs `-Wall -Wextra -Werror` and the nvcc
equivalents, so a successful build is the gate.

## Style

- `snake_case` for functions and files, `PascalCase` for types, `UPPER_SNAKE`
  for constants, a trailing underscore on private members.
- Kernels named by operation and variant, for example `compute_forces_tiled`.
- `.cu` and `.cuh` for device code, `.cpp` and `.hpp` for host code.
- Comments explain physics and constraints. A comment that restates the code is
  noise; a comment explaining why a barrier is where it is, or why a term is
  softened, is the point.

## Adding a benchmark point

`bench_all` skips configurations already present in the CSV from the same commit and
protocol, so a sweep can be interrupted and resumes at the group it lost. Rows from another
commit, format or protocol are replaced, with a printed note. Use `--force` to remeasure. Every
row records the seed, commit, dirty flag, protocol, CUDA runtime and driver versions, fast math
setting and a timestamp, so a number can always be traced back to the tree that produced it.

Configurations being compared go in one group, so they are measured round by round. Absolute
timings move with the state of the card, and `v1.0.0`'s claim that relative differences were
stable to a tenth of a percentage point was wrong when measured in separate blocks. The sweep
measures its own drift at its start, middle and end.
